# Архитектура проекта Portal Robot

Этот файл — карта проекта для сквозных изменений. В текущей конфигурации:

- **3 станка**: `MACHINE_1..3`, по одному `FB_MACHINE` и
  `FB_MACHINE_SIMULATION` на каждый;
- **1 портальный робот** с осями X/Y/Z, одной группой осей и двумя захватами;
- **2 магазина с переключаемым типом**: статичные по 120 мест либо два двухпалетных
  механизма по 2 × 96 мест (384 места суммарно), каждый со своей осью SoftMotion;
  состояние механизма — `GVL_TWO_PALLET/FB_TWO_PALLET`, роботные операции — `FB_MAGAZINE`.
  виртуальные оси `Magazine_1/2` привязаны, в тестовой среде симулируются герконы,
  слой физической привязки I/O подготовлен в `ReadPhysicalInputs/WritePhysicalOutputs`, настройка каналов Device I/O Mapping ещё не выполнена; подробности в [описании магазина](21-two-pallet-magazine-control.md#14-реализация-plc--hmi-24092026);
- **1 автоматическая ячейка**, которой управляет универсальный `FB_CELL_MANAGER`;
- **2 независимых ГК** с отдельными конвейерами, датчиками и `FB_GEOMETRY_CONTROL`;
- **1 журнал аварий и предупреждений**, собираемый `FB_ALARM_MANAGER` из активных
  источников; позиции прежних приводов магазинов зарезервированы для корректного чтения истории.

Реализованное управление механизмом с двумя палетами, одним приводом и тремя
пневмоцилиндрами описано в [21-two-pallet-magazine-control.md](21-two-pallet-magazine-control.md).
Документ содержит обе последовательности обмена,
инициализацию, восстановление и запрет подъёма П2 до завершения выезда П1
и останова каретки в автомате обмена. В ручной наладке подъём не требует
рабочей координаты каретки; шесть герконов конфигураций П1/П2 задаются отдельно.
Обмен палет выключенного магазина разрешён и при работающем автоцикле:
PLC проверяет отсутствие текущей/выданной операции именно с этим магазином и
блокирует новые входы робота в него до завершения смены. Робот может продолжать
работу со станком или другим магазином.
Редактирование операторской палеты не зависит от режима и механики; роботной —
доступно после выключения и освобождения операции этого магазина. Stop неподвижного
механизма и штатная смена режима сохраняют подтверждённую расстановку.
Управляющий алгоритм PLC реализован в `FB_TWO_PALLET`, виртуальные герконы — в
`FB_TWO_PALLET_SIMULATION`. Трёхмерная модель нового магазина находится в
`twoPalletMagazine.ts`; статичные магазины сохранены как альтернативный тип.

## Общая схема

```text
PLC_PRG / FB_*
  -> GVL_HMI
  -> OPC UA server PLC
  -> visu/gateway/server.mjs
  -> WebSocket snapshot
  -> visu/src/plc/client.ts
  -> CellState / PlcRuntimeInfo
  -> React-компоненты и Three.js-сцена
```

Команда идёт обратно через `plcClient.send()` и явный `commandMap` gateway.
PLC повторно проверяет режим, состояние механизма и разрешения безопасности.

Дискретные I/O диагностируются отдельным потоком: `ReadPhysicalInputs` сохраняет
сырой уровень, `ReadIoOverrides` проверяет разрешение подмены, затем работают
фильтры и FB. Общий режим прямого ручного I/O включается при Manual и останове;
при входе запоминает все 47 назначенных DO. `ApplyIoOutputOverrides` завершает
`WritePhysicalOutputs`, напрямую назначая сохранённые ручные уровни без
технологических блокировок. Выход из режима/Auto/потеря аренды возвращает
текущие штатные уровни программы. `ReadIoEmergencyStop/ResetIoEmergencyStop`
обрабатывают отдельный защёлкнутый программный останов до владельцев движения;
снятие не запускает ячейку. После назначения выходов `RecordIoDiagnostics` фиксирует
переходы в FIFO 100 записей и публикует упакованные уровни в GVL_HMI. Gateway
читает согласованный FIFO отдельно от обычного снимка, архивирует новые Seq
в SQLite и передаёт их подменю «Диагностика → Входы и выходы». Владельцем
разрешения и автоматического снятия ручных DI/DO остаётся PLC. HMI имеет
два раздела «Сигналы»/«Переключения I/O», DO слева/DI справа, разворачивание
«Подробнее», прямоугольные карточки с адресом/клеммой и крупным индикатором,
общую кнопку входа в ручное I/O и выбор своего набора сигналов. См.
[23-physical-io-diagnostics.md](23-physical-io-diagnostics.md).

Автоматические тесты используют тот же путь: HMI хранит сценарии в SQLite gateway,
gateway запускает Python runner, runner управляет реальным PLC Runtime через
служебный WebSocket. Для `Python Modbus` runner через локальный test-control API
управляет уже запущенным экземпляром симулятора; второй Modbus Server не
создаётся. Отдельная среда `NORMAL / SIMULATION / SC500_BENCH` не заменяет выбор
интерфейса `SoftMotion / Modbus TCP`.

## CODESYS: программа и связи FB

Точка входа — `Portal_robot/Device/application/PLC_PRG.st`. В ней создаются и
вызываются:

| Блок | Ответственность и связи |
| --- | --- |
| `FB_AXIS` ×3 | Оси портального робота X, Y и Z; статичные магазины собственных осей не имеют |
| `FB_AXIS_GROUP` | Группа XYZ; выдаёт готовность и фактические координаты |
| `FB_SIMULATION_DYNAMIC_LIMITS` | На границе SoftMotion-теста оркестрирует Stop → GroupDisabled → изменение Dynamic Limits X/Y/Z → штатный GroupEnable; при выходе из симуляции возвращает сохранённые пределы |
| `FB_MOTION_MANAGER` | Движение по именованным точкам через группу осей |
| `FB_POINT_MANAGER` | Проверяет и выдаёт точки станков и магазина; 12 редактируемых базовых точек хранятся в `PERSISTENT RETAIN` |
| `FB_MACHINE` ×3 | Состояния, двери, патрон, цикл и команды каждого станка |
| `FB_MACHINE_SIMULATION` ×3 | Моделирует I/O станков и возвращает его в `FB_MACHINE` |
| `FB_MAGAZINE` ×2 | Одна статичная кассета на 120 слотов и пошаговый автомат TAKE/PUT/CHANGE/RETURN_BLANK через `MAGAZINE_SAFE`, `MAGAZINE_CHANGE`, `MAGAZINE_IN_SLOT` |
| `FB_ROBOT` | Координирует движение, два захвата, станки, магазин и Modbus |
| `FB_ROBOT_MODBUS` | Modbus TCP Client: FC03/FC16, heartbeat, `CommandSeq/AckSeq`, декодирование SC-500 |
| `FB_CELL_SAFETY` | Нормализует дискретные входы безопасности, формирует `xGlobalError`, управляет четырьмя замками/лампами, импульсом сброса реле и физическими кнопками ячейки; содержит отдельный fault injector |
| `FB_CELL_MANAGER` | Единый автоматический цикл для 1–3 типов: выбирает совместимый станок и формирует команды роботу, станкам и магазину |
| `FB_ALARM_MANAGER` | Собирает первичные аварии и предупреждения в журнал |

Связи цикла:

1. `GVL_HMI` принимает команды ячейки, робота, станков, магазина и отдельный сброс реле безопасности.
2. После чтения HMI `PLC_PRG.ReadPhysicalInputs` в `NORMAL` фильтрует дискретные входы и назначает их владельцам; в тестовых средах станки используют модели; захваты SoftMotion получают модель, Modbus — статусы SC-500. В конце скана штатный слой `WritePhysicalOutputs` переносит команды на проверенные физические каналы в `NORMAL`; активный прямой ручной слой назначает DO отдельно от этого допуска. Карта и ограничения — [22-physical-io-mapping.md](22-physical-io-mapping.md). После чтения физических входов `PLC_PRG.RunSafety` вызывает `FB_CELL_SAFETY`, переносит физические `Старт/Стоп/Сброс` в общий интерфейс ячейки и публикует аппаратные выходы через `GVL_CELL_SAFETY_IO`.
3. `PLC_PRG` передаёт команды в `GVL_CELL_CONTROL`, `FB_CELL_MANAGER`, `FB_MACHINE`,
   два `FB_MAGAZINE` и `FB_ROBOT`.
4. `FB_CELL_MANAGER` использует статусы трёх станков, робота, двух магазинов,
   готовность осей и `FB_CELL_SAFETY.Status.xReady`, затем формирует команды автоматического обслуживания.
5. `FB_ROBOT` получает команды трёх станков, магазина и ячейки, использует
   `FB_MOTION_MANAGER`, `FB_POINT_MANAGER` и `FB_AXIS_GROUP`.
6. `FB_MACHINE_SIMULATION` возвращает I/O-статусы в соответствующие станки.
7. Статусы, диагностика и ошибки копируются в `GVL_HMI`: `stCell*`, `stCellSafety*`, `stRobot*`,
   `astMachine*`, `astMagazine*` и `stAlarm*`.

Журнал сохраняет 19 числовых позиций: 17 активных источников (ячейка, робот,
станки 1–3, два магазина, оси X/Y/Z, группа осей, motion manager, point manager и
gripper, дискретная безопасность, ГК 1/2) и две зарезервированные позиции прежних приводов магазинов. Резерв нужен
только для чтения старых записей SQLite и не участвует в активной диагностике.
Каскадные ошибки не должны дублировать первопричину.

## Структура PLC

```text
Portal_robot/Device/application/
|-- FB/       функциональные блоки и методы
|-- GVL/      глобальные переменные, включая GVL_HMI
|-- ST/       DUT, структуры и перечисления
|-- PLC_PRG.st
|-- Symbols.xml
`-- Task Configuration.xml
```

Python-симулятор внешнего контроллера находится в `robot_simulator`. Он не
входит в цикл PLC: отдельный `RobotModel` исполняет команды и формирует обратную
связь, `RobotModbusServer` публикует holding registers, а PySide6-интерфейс
имитирует локальный пульт робота. Локальный `RobotControlApiServer` предоставляет
runner эксклюзивную lease-сессию для FAST и аварийных инъекций. Конфигурация
точек и геометрии магазина внешнего контроллера принадлежит симулятору и
сохраняется в его `config.json`.

Режим робота хранится в RETAIN-GVL и выбирает единственный источник обратной
связи. В SoftMotion координаты и готовность поступают от группы XYZ; в Modbus —
от `FB_ROBOT_MODBUS`. Технологические блоки в обоих режимах используют общий
`ST_ROBOT_COMMAND` и `ST_ROBOT_STATUS`. Карта внешнего контракта описана в
[08-sc500-modbus-register-map.md](08-sc500-modbus-register-map.md).

Для магазинного движения `ST_ROBOT_COMMAND` содержит пару `uiMagazineId + iActiveSlot`.
В SoftMotion единственный обработчик команды рассчитывает XYZ по базе выбранного
магазина, а в Modbus контроллер робота делает тот же расчёт. Высокоуровневая операция
магазина никогда не передаётся роботу одной командой.

Матрица магазина фиксирована как 12 × 10. Общий шаг X/Y меняется через
`ST_MAGAZINE_HMI_COMMAND` только при выключенных обоих магазинах. Signed-смещения
`MagazineSafeZ` и `MagazineChangeZ` принадлежат `ST_POINT` и сохраняются вместе с
базовой точкой конкретного магазина в `PERSISTENT RETAIN`. Базовая точка магазина
считается настроенной только при ненулевых значениях обоих смещений. Для
`MAGAZINE_SAFE` и `MAGAZINE_CHANGE` целевая координата вычисляется как
`Z базовой точки + смещение`; отрицательная величина поднимает портал,
положительная опускает.

Перед изменением FB нужно прочитать его DUT, GVL, методы, вызов в `PLC_PRG.st` и
потребителей его статусов. Бинарный `.project` и XML вручную не редактируются;
экспорт Codescribe хранится вместе с исходниками.

## Структура визуализации

```text
visu/
|-- gateway/server.mjs       OPC UA browse/read/write и WebSocket
|-- src/App.tsx              компоновка, страницы и локальное состояние
|-- src/components/ui        общие UI-компоненты
|-- src/components/machine   карточки станков
|-- src/components/magazine  матрица и статистика магазина
|-- src/components/CellViewport.tsx  контейнер 3D-сцены
|-- src/model                CellState, layout, defaults, scenarios
|-- src/plc/client.ts        snapshot -> модель HMI, команды и аварии
|-- src/styles               тема и глобальные стили
|-- src/three                portal, machines, magazine и эффекты
`-- src/assets               GLB, логотипы и текстуры
```

`App.tsx` управляет страницами `monitoring`, `machines`, `robot`, `magazine`,
`manual`, `events`, `alarms`, `settings`, `statistics`, `admin` и нижними областями `cell`, `machines`,
`robot`, `magazine`. `CellState` содержит один `RobotState`, три `MachineState`
и два `MagazineData`, каждый с одной статичной кассетой на 120 слотов.

`gateway/server.mjs` динамически ищет `GVL_HMI`, публикует snapshot и разрешает
только команды из `commandMap`. `client.ts` преобразует числовые коды в текст,
состояния и `PlcAlarmEvent`; React передаёт результат карточкам и экранам.

Раздел «Диагностика» в операционном меню получает отдельный опрос OPC UA от gateway.
Он читает стандартные узлы `ServerStatus`, версию и время запуска сервера, а также
существующий `GVL_HMI.udiPlcHeartbeat`. Неизменный счётчик в течение 4 секунд при
доступном OPC UA означает отсутствие циклов PLC-программы: возможен STOP приложения
или остановка задачи. `ServerStatus.State=Running` относится только к серверу OPC UA
и не подтверждает RUN приложения. Опрос не зависит от PLC-аварий и продолжает
работать при STOP, пока доступен сам OPC UA Runtime. Позже в этот раздел можно
добавить фактические I/O ячейки.

Пользовательские учётные записи и серверные cookie-сессии хранятся gateway в
отдельной SQLite-базе. Без действующей сессии обычный WebSocket работает только
для просмотра телеметрии и отклоняет управляющие команды. Управление
пользователями доступно администратору; см.
[11-user-accounts.md](11-user-accounts.md).

Полноэкранный раздел администрирования доступен из профиля и оставляет верхний
бар HMI на месте. Он содержит редактор статистики и управление тремя архивами:
статистикой, журналом событий и циклограммой. Сроки хранения и отдельный аудит
операций хранятся в `visu/gateway/data/archive-policy.sqlite`.

Смысловая история работы ячейки хранится gateway в SQLite на компьютере. Она
включает переходы оборудования, действия оператора, аварии и события связи;
см. [10-cell-event-log.md](10-cell-event-log.md).
Физический факт выпуска формирует PLC: магазин или ГК увеличивает свой монотонный счётчик
после подтверждённой укладки готовой детали. Gateway превращает приращения
счётчика в исторические события, привязывает их к авторизационным интервалам и
рассчитывает план/факт; см. [14-operator-shifts-statistics.md](14-operator-shifts-statistics.md).
`CellViewport` создаёт `cellScene`, которая обновляет один портал, три модели
станков и два статичных магазина без пересоздания сцены на каждый рендер.
Редактор SoftMotion публикует 14 базовых точек: по три на станок
(`ABOVE`, `CHUCK_APPROACH`, `CHUCK`), `HOME_SAFETY`, две базы магазинов и две базы ГК.
Прежние 12 точек обязательны для готовности робота; ГК проверяет свою базу
и SAFE_Z при включении. Общий редактор и расширенная наладка ГК используют
одну конфигурацию станции с отдельными владельцами NORMAL/SIMULATION. Базы
ГК сохраняются без технологических блокировок по отдельному допуску связи,
SoftMotion и валидных лимитов; режим, движение и восстановление станции
не ограничивают SAVE. Непроверенная станция показывает «Указать состояние ГК»;
подтверждение пустоты не включает её.
Точки `MACHINE_1..3_INSIDE` оставлены только как legacy-коды протокола и не входят в
редактор или проверку готовности. Gateway сохраняет JSON-копии текущего
PLC-снимка только в `visu/gateway/data/point-backups` (путь можно задать на
сервере через `POINT_BACKUP_DIR`). Формат экспорта версии 2 содержит 14 точек;
старые копии версии 1 мигрируют при чтении: прежние данные сохраняются,
базы ГК добавляются ненастроенными, оригинал файла не меняется.
HMI не открывает проводник и не принимает
произвольный путь: оно показывает проверенный gateway список файлов из этой
папки, а импортирует настроенные значения последовательными подтверждаемыми
транзакциями `SAVE`. Gateway проверяет формат, версию, размер, индексы,
`PointId`, координаты, скорость и магазинные Z-смещения, запрещает выход из папки
и символические ссылки. Старые документы версии 1 без магазинных смещений
нормализуются значениями `0/0`: координаты импортируются, но магазинная точка
остаётся ненастроенной до явного ввода Safe Z и Change Z.
Gateway дополнительно формирует из `lrActualX/Y/Z` единый координатный кадр с
локальным номером и нормализованным `sourceTimestamp` OPC UA. 3D-портал
воспроизводит очередь таких кадров с отставанием 250 мс и критически затухающим
фильтром положения; это сглаживание не участвует в управлении, авариях и PLC.

## Где менять типовые вещи

| Результат | Основные места |
| --- | --- |
| Новый элемент или карточка | `visu/src/components`, `App.tsx`, Storybook |
| Новый PLC-статус | `GVL_HMI` → `gateway/server.mjs` → `src/plc/client.ts` → модель/компонент |
| Новая авария HMI | `src/plc/client.ts`, `AlarmScreen`, сводка аварий |
| Новая 3D-деталь | `src/assets/models`, `src/three`, `CellViewport` |
| IP и запуск | `visu/gateway/server.mjs`, переменные окружения, `package.json` |

## Геометрический контроль

Два независимых `FB_GEOMETRY_CONTROL` работают в NORMAL и с отдельными
`FB_GEOMETRY_CONTROL_SIMULATION` в SIMULATION, только с SoftMotion.
`RunGeometryControl` исполняется перед менеджером ячейки, `PublishGeometryControl`
после робота/выходов. Вызов запоминает станок и тип; менеджер выбирает свободный
ГК, ждёт либо направляет деталь в магазин с точным назначением в журнале.
Расширенный контракт, точки24–29, восстановление, SQLite и HMI: [24](24-geometry-control.md).
