# Экономная работа с Codex

Цель — загружать в задачу только правила и файлы нужной области: PLC, HMI или
Three.js. Общая история и повторение кода быстро увеличивают расход токенов.

## Как ставить задачу

Один запрос должен описывать один связный результат:

```text
Задача: <что должно измениться>.
Область: <точные папки, файлы, FB или компонент>.
Поведение: <сейчас> -> <должно быть>.
Не менять: <контракты, соседние блоки, OPC UA, 3D>.
Проверка: <build, test, CODESYS compile или скриншот 1920x1080>.
В ответе: <краткий отчёт и изменённые файлы>.
```

Не пересказывать проект и не вставлять код, который уже находится на диске.
Достаточно назвать путь, FB, компонент или метод.

## Когда начинать новую задачу

- завершён крупный этап;
- работа переключилась между PLC, HMI и 3D;
- начался новый экран или функциональный блок;
- старый чат содержит неактуальные итерации.

Один чат должен соответствовать одному результату: экрану, журналу аварий,
интеграции GLB или алгоритму магазина. Не создавать задачу для каждого пикселя;
видимые правки лучше перечислить одним списком.

## Выбор модели и reasoning

| Задача | Модель и уровень |
| --- | --- |
| Поиск, переименование, Markdown, запуск сборки | Luna, `low`/`none` |
| Понятная правка FB, React, OPC UA mapping, Three.js, тесты | Terra, `medium` или `low` |
| Архитектура ячейки, SM3, сложная диагностика, сквозной review PLC + HMI | Sol, `high` |

`high`, `xhigh` и `max` не нужны для цвета, отступа, простого CSS, `npm run build`
или механического переноса уже принятого паттерна. Максимальный уровень
оставлять для задач, где ошибка влияет на движение, безопасность, автомат
состояний или контракт блоков.

## Как не тратить токены повторно

- Не смешивать в одном запросе автомат PLC, новый дизайн, GLB, очистку Git и push.
- Не отправлять серию уточнений «выше/левее/иконку больше»; отметить расхождения
  одним скриншотом и списком.
- Не повторять правила из `AGENTS.md`; читать ближайший файл инструкций.
- Сразу указать границу полномочий: «только анализ» или «реализуй и проверь».
- Реализацию и проверку просить одним запросом, затем проверить один критерий
  готовности.

## Рабочий цикл

1. Выбрать один результат и точную область.
2. Проверить существующие типы, вызовы, mapping и похожий компонент.
3. Реализовать локально, не меняя несвязанные файлы.
4. Запустить подходящую проверку: CODESYS Build, `npm run build`, тест или
   визуальную сверку.
5. После законченного логического изменения показать `git diff` и сделать
   локальный commit, если он запрошен.
6. Push — отдельное действие только по явной просьбе.

## Быстрый чек-лист

- [ ] Один связный результат и точный путь.
- [ ] Описаны текущее и ожидаемое поведение.
- [ ] Указано, что нельзя менять.
- [ ] Есть критерий готовности.
- [ ] Не повторён доступный на диске код.
- [ ] Выбрана модель не мощнее необходимого.
- [ ] `node_modules`, `dist`, логи и временные файлы не включены в commit.
