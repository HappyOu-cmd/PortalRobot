# Аварии и восстановление ячейки: офлайн-аудит 29.10.2026

Это исторический отчёт **до исправлений**. Текущие изменения и повторные
проверки F001–F006 находятся в [реестре 29](29-cell-defect-register.md).

Найдены три дополнительных дефекта, воспроизводимые при **одном типе изделия**.
Наиболее существенный — потеря физического Alarm станка в NORMAL (F006).
F004/F005 — гонки общего сброса: после устранения причины первый Reset оставляет
зависимые ошибки, второй отдельный Reset помогает. В проверенных сценариях
вечной взаимной блокировки после корректного ремонта не обнаружено.

Ранее найденный F003 также относится к одному типу: отказ отдельного UNLOAD до
взятия детали создаёт постороннюю ошибку магазина. Только F001/F002 требуют
нескольких типов. Подробности первого аудита: [отчёт 27](27-offline-cell-model-audit.md).

PLC-исходники, проект CODESYS, HMI и gateway не изменялись. Исправления ниже
являются направлениями разработки, а не выполненными правками или инструкцией
восстановления физического оборудования.

## F006: реальная авария станка теряется в NORMAL

Приоритет P1. Число типов и выбранный магазин на причину не влияют.

Цепочка рабочего кода:

1. `PLC_PRG.ReadPhysicalInputs.st:136/147/158` переносит физический Alarm в
   `GVL_MACHINE.astPhysicalInput[1..3].xAlarm`.
2. `PLC_PRG.ReadHmiInputs.st:114` принудительно выключает инъекцию в NORMAL.
3. `PLC_PRG.RunMachines.st:73` выбирает физический снимок для NORMAL, но затем
   **во всех средах** передаёт его через MACHINE_1/2/3_FAULT (`:80–98`).
4. `FB_FAULT_INJECTOR/FB_MACHINE_FAULT_INJECTOR.st:30` заменяет Alarm выражением
   `MachineStatusRaw.xAlarm AND Request.xEnabled AND (три тестовых переключателя)`.
   Поэтому при выключенной инъекции реальный TRUE превращается в FALSE.
5. `RunMachines.st:134` и аналогичные вызовы С2/С3 передают в FB_MACHINE именно
   этот изменённый статус. Публичный `Status.stIo` также получает его.

Исполнение текущего ST в Python дало:

| Наблюдение | Фактический результат |
| --- | --- |
| Физический Alarm | TRUE |
| Request.xEnabled | FALSE |
| Alarm, полученный FB_MACHINE | FALSE |
| Ошибка станка при исходном IDLE | 0 |
| Разрешение принять обслуживание | TRUE |
| ResetAllowed для заранее имеющейся ошибки при том же физическом Alarm | TRUE |
| Ошибка после Reset при удерживаемом физическом Alarm | 0, состояние DISABLED |

В Python дополнительно исполняется весь `PLC_PRG.RunMachines.st` в NORMAL,
включая выбор входов и три вызова станков. Потеря входа независимо подтверждена
исполнением того же инжектора существующим Node ST runtime. Ожидаемое поведение
закреплено strict-xfail для С1, С2 и С3; допустим только AssertionError,
неподдержанная конструкция модели не засчитывается как найденный дефект.
Физический шкаф/станок при проверке не использовался; состояние загруженной
программы относительно этих файлов не устанавливалось.

**Направление исправления:** реальная обратная связь в NORMAL должна проходить
без фильтра тестовыми переключателями. Сохранить отдельную логику снятия
защёлкнутой виртуальной аварии в SIMULATION: безусловное изменение одной строки
может изменить существующий сброс симулятора. Нужен явный выбор источника/среды
у границы инжектора и проверки всех трёх станков при Alarm, Reset, переключении
среды и включённых/выключенных тестовых переключателях.

## F004: магазин повторно защёлкивает ошибку, пока сбрасывается группа

Приоритет P2. Воспроизведён в статичном и двухпалетном режиме; один тип.

Вход: М1 выполняет TAKE; робот находится в его контексте. Возникает ошибка
группы, затем физическая причина устранена, движение остановлено, выбран Manual.
Оператор подаёт разрешённый импульс общего Reset.

| Скан модели | Состояние после скана |
| ---: | --- |
| 71 | М1 снял ошибку; группа ещё ошибочна; робот ERROR=2, попытка сброса pending |
| 72 | М1 снова видит старую ошибку робота и защёлкивает ERR_ROBOT=32 |
| 73 | Группа исправна, робот завершил принятый сброс; М1 всё ещё ERROR=32 |
| 74 | М1 требует зависимый Stop; робот снова ERROR=16 |
| 87 | Второй отдельный Reset очищает обе ошибки |

Причина: `FB_MAGAZINE.st:451` допускает общий сброс при опубликованном
`stRobotStatus.xResetAllowed`; ветка ERROR (`:1138`) сразу снимает ошибку и
контекст. Но общий сброс группы асинхронный (`PLC_PRG.RunMotion.st:172`).
В следующем скане проверка `FB_MAGAZINE.st:603` видит ещё не очищенный ERROR
робота и возвращает ERR_ROBOT. Затем `FB_ROBOT.st:277` формирует новый каскад.

После второй попытки проверены HOME, отдельный новый Start и ещё 420 сканов
работы без ошибки. Это **повторное защёлкивание**, а не доказанная вечная
блокировка. Задержки ответа группы 2/4/8 сканов проверены в обоих режимах.

**Направление исправления:** согласовать время жизни принятой попытки сброса
первичного и зависимого владельца. Зависимая ошибка должна дождаться завершения
исходной попытки, не превращая старый снимок первичной ошибки в новый отказ.
Новую первичную ошибку, Stop, потерю условий и timeout попытки требуется
обрабатывать отдельно; просто скрывать ERR_ROBOT на несколько сканов нельзя.

## F005: робот сбрасывается раньше окончания Reset ГК

Приоритет P2. Один тип, реальный Call и рецепт доставки на ГК1.

Вход: ошибка привода ГК во время взаимодействия с роботом, затем физическая
причина устранена. Reset ГК длится 1 с, состояние и зависимый Stop до его конца
сохраняются. Общий импульс одновременно сбрасывает робота.

| Скан модели | Состояние после скана |
| ---: | --- |
| 294 | Робот уже IDLE, ГК ERROR=1 и ResetBusy=TRUE |
| 295 | У ГК ещё активен RobotStopRequired; робот повторно ERROR=16 |
| 304 | Reset ГК завершён, его ошибка снята; робот остаётся ERROR=16 |
| 310 | Второй отдельный Reset возвращает робота в IDLE |

`FB_GEOMETRY_CONTROL.st:223–229` правильно сохраняет ошибку до конца импульса;
`:289` продолжает публиковать зависимый Stop. Но `FB_ROBOT.st:710` очищает
принятую попытку без ожидания этого оборудования, а `:277` на следующем скане
защёлкивает Stop заново. Второй Reset, HOME и новый Start успешны; ещё 420 сканов
не создают ошибки. Занятость и счётчик подтверждённой укладки не сбрасываются.

**Направление исправления:** принятая попытка сброса робота должна согласованно
дождаться терминального результата сброса первичного ГК. Не снимать занятость,
не запускать ленту автоматически и не игнорировать новое требование Stop.
Отдельно проверить отказ сброса, удерживаемый Alarm, Stop во время импульса и
разные соотношения длительности импульса/таймаута попытки.

Полный каталог каждого фиксированного теста и его входов:

| Порядок действий, роли и удерживаемые причины | 23 | Все 6 перестановок Repair/Reset/Stop, 12 комбинаций ролей/причин, 5 удерживаемых причин/команд |

| Физический Alarm в NORMAL | 3 | Strict-xfail F006 для С1–С3 |

Путь восстановления использует команды владельцев: устранение причины,
согласованная остановка, Reset, открытие люка по опубликованному recovery-допуску
при необходимости, подтверждение состояния станка/груза, HOME, включение и новый
Start. После согласованной остановки Reset/HOME не меняют занятость захватов
и записанные слоты. Для ГК отдельно проверяются сохранение выпуска/укладки,
снятие резерва и явное подтверждение оператором пустоты.

Safety исполняется отдельной матрицей; интеграционные сценарии получают
агрегированный GlobalError. Движение XYZ, ответ reset привода, торможение и
механика оси магазина — ограниченная модель среды. Кинематика, столкновения,
электрические цепи, отказы/обрыв каждого отдельного физического датчика и
внутренняя библиотека SoftMotion не эмулируются. HOME в модели не подтверждает
безопасность прямого перемещения к HOME на реальном оборудовании.

Проверки заранее заданного ERROR не доказывают обнаружение каждой первичной
причины. Произвольные многократные аварии, все сочетания всех масок, перезапуск
PLC с RETAIN/PERSISTENT и все физические задержки не перебраны. Для Modbus
дополнительно выполнены существующие независимые Node-проверки: записи
Reset=1/0, свежий IDLE, FC03/FC16 failures, reconnect, Stop, CommandSeq/AckSeq и
отсутствие автоматического повтора. Новый Python-интегратор использует SoftMotion.
