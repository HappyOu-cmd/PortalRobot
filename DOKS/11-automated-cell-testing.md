# Автоматизированное тестирование логики ячейки

Прогоны во вкладке «Сценарии и тесты» исполняет настоящая программа PLC Runtime.
Gateway — единственный владелец OPC UA-записи; Python-runner управляет прогоном
через служебный WebSocket. Локальные проверки исходников не подключаются к PLC.

## Экран тестов

Вкладка **«Запуск и результаты»** содержит выбор набора или одного фиксированного
случая, запуск, управляемую остановку, прогресс и историю. В списке результатов
можно оставить только ошибки. Выбранный случай показывает причину результата,
этап, таблицу «Ожидали / Получили», подтверждения команд и снимок при сбое.
Доказательства сохраняются и для PASS; старые отчёты без них остаются доступны.

Кнопка **«?»** рядом с «Запуск проверки» открывает справку по всем восьми наборам:
состав проверок, условия запуска и критерии успеха. Выбранный набор раскрывается
сразу; точные названия, описания и количество фиксированных сценариев берутся
из того же каталога gateway, что и список запуска. Справка доступна и во время
прогона; её открытие не отправляет команд в PLC.

Вкладка **«Сценарии»** содержит библиотеку, редактор, копирование, удаление и
снятие текущего состояния PLC. Снимок требует остановленной ячейки, известной
расстановки палет и пустых ГК; непредставимое начальное состояние отклоняется
с причиной. Тип магазинов, станки, захваты, обе стороны палет,
вызовы ГК, маски ошибок и ожидания редактируются здесь. Нажатие на слот выбирает
его; содержимое и общий тип задаются над матрицей. ПКМ не требуется.

Источник запуска задаётся явно: «Штатные наборы» либо «Сохранённые сценарии».
Отметки в библиотеке не заменяют незаметно выбранный штатный набор.
Параметры среды, интерфейса и скорости находятся в раскрываемом разделе.
Ползунок скорости хранит локальное требование до запуска, без записи в PLC.

## Подготовка следующего прогона с PLC

1. Импортировать обновлённые ST-исходники, DUT тестов и методы `PLC_PRG` в CODESYS,
   пересобрать Symbol Configuration и проект. Компиляцию и загрузку выполняет пользователь.
   `stTestObservability.uiSchemaVersion` должен публиковать `3`; старый PLC блокирует
   запуск до каких-либо команд runner.
2. PLC должен быть в RUN. Настроить требуемые базовые точки и проверить готовность
   робота. Тип магазинов выбрать **до сессии**: он никогда не переключается runner.
3. Для двухпалетных тестов заранее применить **SIMULATION + SoftMotion**, подготовить
   и подтвердить расстановку **обоих** магазинов. Разрешены оба сочетания физических
   палет у робота. Приводы могут оставаться включёнными и неподвижными; загрузка
   запрещена при движении, неизвестной роли палеты или неподтверждённой расстановке.
   Переключение среды по-прежнему требует выключенных приводов магазинов.
4. Для ГК проверить базы включаемых станций. ГК поддерживается только в SoftMotion;
   соответствующие сценарии работают в SIMULATION. Подтверждение пустоты и включение
   виртуальных лент runner выполняет штатными командами после загрузки сценария.
5. Запустить gateway/HMI, выбрать набор либо один случай и нажать «Запустить проверку».
   Этот запуск уже управляет PLC: останавливает текущий цикл и получает эксклюзивную
   тестовую сессию. Во время разработки задачи такие запуски не выполняются.

Для Python Modbus требуется заранее запущенный `robot_simulator/run_simulator.bat`
с Modbus Server и локальным Test API (`127.0.0.1:8765`, либо `ROBOT_SIM_CONTROL_URL`).
Runner использует этот экземпляр, второй сервер не создаёт. Для этого интерфейса
доступны статичные сценарии без ГК. Стенд SC-500 требует `sc500-modbus`, Realtime
и статичные магазины. Физический ключ стенда не используется.

## Наборы

| Набор | Случаев | Магазины и среда |
| --- | ---: | --- |
| Приёмка / Acceptance | 143 / 149 | Статичные / двухпалетные; SIMULATION + SoftMotion |
| Аварии и восстановление / Recovery | 66 | Текущий тип; SIMULATION + SoftMotion |
| Основные / Smoke | 12 | Статичные; либо обе палеты в SoftMotion SIMULATION |
| Регрессия / Regression | 75 | Те же варианты; первый владелец ошибки, типы и восстановление |
| Магазины и палеты | 8 | Двухпалетные, SoftMotion SIMULATION |
| Геометрический контроль | 8 | Оба типа магазинов, SoftMotion SIMULATION |
| Полный цикл / General | 8 | Четыре статичные партии М1-A → М2-A → М1-B → М2-B, SIMULATION |
| Сгенерированные / Generated | 1–1000 | Текущий тип магазинов; повторяемые seed и count |

После изменений ПО выбирайте **«Приёмка» → «Весь набор»**. Это выбор по умолчанию.
В неё входят 67 проверок штатной Regression (Smoke однократно), 66 причин с
восстановлением, восемь маршрутов ГК и завершающая проверка магазинов:
для статичных — General №1–2, для двухпалетных — все восемь сценариев палет.
Прежние Smoke №10 и Regression №13–19 доступны отдельно для диагностики,
но в приёмке заменены более строгими проверками продолжения производства.
Первый FAIL завершает приёмку; неполный прогон не считается PASS.
Статичная приёмка длительная: два сценария по четыре партии по 120 изделий.
Тип магазинов не переключается: другой тип проверяется отдельным прогоном.

Recovery требует новую запись журнала PLC с точным источником и кодом,
запрет Start, устранение причины, один общий Reset, ручной возврат в HOME,
включение оборудования и новый выпуск. После обнаружения ошибки Apply больше
не вызывается; все исходные изделия должны стать готовыми деталями в магазинах.
Если частично заполненный магазин после выпуска ожидает оператора, runner
подаёт штатный Stop после подтверждения результата.
При таймауте зажима патрона отдельно проверяется совместное удержание одной
заготовки патроном и захватом: после Reset патрон разрешённой ручной командой
разжимается до HOME. Без подтверждения положения/захвата тест завершается FAIL.
Этап отказа и сравнения сохраняются в существующих результатах прогона.
После потери подтверждения палет runner подтверждает только прежнюю расстановку:
кандидат должен совпасть с исходной физической палетой; команда использует текущую
ревизию PLC и его `xConfirmAllowed`. Движение, требование Home или другая палета
завершают проверку отказом, без автоматической перестановки инвентаря.
Сохранённый Recovery с другим числом типов, начальным грузом или включёнными ГК
отклоняется до тестовой сессии: его операторские ответы рассчитаны на описанную
однотипную конфигурацию. Обычные многотипные сценарии остаются в Regression.

Состав, необходимость каждого прежнего фиксированного сценария и границы
покрытия ошибок: [аудит тестов и приёмка](31-test-coverage-and-acceptance.md).
В частности, 66 причин не означают все аппаратные отказы и все сочетания аварий.

`GET /api/test-catalog` получает имена, описания и номера из Python-источника.
`POST /api/test-runs` принимает `suite`, необязательный `fixedCaseIndex` с 1 либо
`scenarioIds`. Фиксированный случай и сохранённые сценарии вместе запрещены.
Для Generated фиксированный номер не используется. Каждый десятый generated-случай
намеренно некорректен и должен получить `result=2`; для двухпалетной формы ошибка
сохраняется в слоте 96 вместо статичного слота 120.

Входы и результаты каждого фиксированного случая перечислены в
[человеческом каталоге](20-smoke-and-integration-test-catalog.md).

## Тестовый контракт v3

Сценарий содержит `magazineMode`, три состояния станков, захваты, ориентацию,
маски первичного владельца ошибки, магазины и настройки вызовов ГК.

- В статичном режиме `magazines[].slots` содержит 120 позиций.
- В двухпалетном режиме `slots` содержит 96 позиций **у робота**, `operatorSlots`
  — 96 позиций **у оператора**, плюс `operatorLoaded` и `autoSwap`. Это две
  разные физические палеты. PLC определяет их номера по подтверждённому
  `uiRobotPallet` в момент загрузки; номер и положение механизма сценарий не меняет.
- Общая конфигурация типов слотов совпадает во всех палетах. Неиспользуемый хвост
  97–120 очищается. Выключенные палеты также входят в баланс инвентаря.
- `geometry.enabled[2]`, `geometry.calls[3]`, `geometry.waitWhenOccupied` задают
  свободные виртуальные станции, принудительные начальные вызовы и политику ожидания.
  Начальные занятые ГК не подделываются: сценарии создают занятость реальной доставкой.
- Старые v1/v2 сценарии читаются как статичные и нормализуются в v3 при сохранении.
  Скрывать двухпалетные данные в старой схеме нельзя.

Gateway сначала проверяет форму **всего** буфера, затем пишет поля
`GVL_HMI.stTestScenario`; новый ненулевой `udiLoadSeq` и Apply идут последними.
Ошибка любой записи не публикует Apply. PLC проверяет версию, выбранный режим,
границы, типы изделий и владельца ошибки до изменения инвентаря; отвечает
соответствующим `udiTestScenarioAckSeq`: `0` — принят, `1` — занят, `2` — неверные данные.

Повторная загрузка перед стартом синхронизирует состояние после приведения захватов.
Runner проверяет не только суммарное количество, но и точное содержимое слотов,
физические владельцы палет и состояния станков. Баланс включает все четыре палеты,
станки, оба захвата и занятые ГК; проекция активной палеты повторно не считается.

Загрузка в SIMULATION очищает только виртуальные память/вызовы ГК и сохраняет
монотонные счётчики выпуска. Автоматический вызов временно выключается ради
воспроизводимости; исходные Auto/Wait сохраняет PLC при первом принятом сценарии
и восстанавливает при снятии тестовой сессии, включая резервную очистку gateway.
Нормальная память ГК не перезаписывается тестовым состоянием.

## Завершение и диагностика

Stop/Abort управляемо останавливает прогон. Очистка ждёт остановки цикла, сбрасывает
инъекции, останавливает виртуальные конвейеры, возвращает изменённые среду,
скорость и интерфейс и освобождает сессию симулятора. При аварийном завершении
runner gateway выполняет резервную очистку только если управление PLC уже началось.
Отказ на предварительной проверке не запускает очистку оборудования.

Отказ команды gateway возвращается с исходной причиной сразу; он не скрывается
за тайм-аутом ожидания. Отчёт содержит LoadSeq/Ack, выбранные станок/магазин,
магазин возврата, вызовы ГК и при Modbus фактический CommandSeq из регистра записи
8, AckSeq, регистры команды, состояние выполнения и ResultCode.

SQLite `visu/gateway/data/tests.sqlite` хранит библиотеку и прогоны.
`test_case_result.diagnostics_json` добавляется совместимой миграцией; старые
строки сохраняются. При локальных проверках используются только временные
или находящиеся в памяти базы, рабочая база журнала не изменяется.

## Проверки без контроллера

Из корня рабочей папки: **`.\verify.cmd`**. Один запуск выполняет все Python-тесты
симулятора/исполнителя ST, все Node-тесты gateway/HMI/PLC-контрактов, проверки
инструментов проекта и `npm run build`. Логи слоёв и `summary.json` с SHA-256 ST
пишутся в `%TEMP%/PortalRobot-checks/<время>`; `--report-dir <путь>` задаёт каталог.
Любой отказ или отсутствующий инструмент возвращает ненулевой код.
Контроллер, CODESYS и рабочие базы не используются; HTTP-интеграция gateway
работает с закрытым тестовым OPC UA endpoint и временными базами.

В `robot_simulator`: `.\.venv\Scripts\python.exe -m pytest`.
В `visu`: `npm run test:automation`, `npm run test:gateway`, `npm run test:ui-state`
и `npm run build`.

Локальный исполнитель проверяет фактические фрагменты ST: атомарность загрузки,
все сочетания ролей палет, запреты, маршруты ГК, обмен в одном слоте, резервирование
и восстановление. Отдельно проверяются Python-runner с транспортом в памяти,
сохранение отчётов, несовместимые контракты и UI-состояния. Это не компиляция
CODESYS и не подтверждение работоспособности на оборудовании. Внешний вид вкладки
проверяет пользователь; браузерные скриншоты в этой задаче не создаются.
