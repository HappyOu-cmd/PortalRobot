# Автоматизированное тестирование логики ячейки

Тест всегда исполняет настоящую программу PLC Runtime. Gateway остаётся единственным владельцем OPC UA-записи, Python управляет прогоном через служебный WebSocket, HMI хранит и редактирует сценарии.

## Быстрый запуск теста

### Однократная подготовка

1. Импортировать тестовые DUT, GVL, POU и метод `PLC_PRG.RunTestControl` в
   CODESYS, обновить Symbol Configuration, собрать проект и загрузить его в PLC.
2. Подготовить Python-runner:

   ```powershell
   cd 'C:\Users\KOKSHAROV IR\Desktop\Project\Portal robot\robot_simulator'
   python -m venv .venv
   .\.venv\Scripts\python.exe -m pip install -e ".[dev]"
   ```

3. Установить зависимости HMI командой `npm install` в каталоге `visu`.

### Каждый запуск

1. Перевести CODESYS Application в `RUN`. Ячейка должна быть остановлена,
   аварии сброшены, робот и технологические блоки не должны выполнять команду.
2. Запустить HMI и gateway в одном окне PowerShell:

   ```powershell
   cd 'C:\Users\KOKSHAROV IR\Desktop\Project\Portal robot\visu'
   npm run dev:live
   ```

3. Открыть `http://127.0.0.1:5173`, затем выбрать
   **Меню → Сценарии и тесты**. В верхней строке должна отображаться связь с PLC.
4. Для первой проверки выбрать:

   - `Smoke — 12`;
   - `SoftMotion` и `Симуляция`;
   - `Fast` для ускоренного либо `Realtime` для обычного времени;
   - снять отметки с сохранённых сценариев, если требуется штатный набор Smoke.

5. Нажать **Запустить**. Runner сам остановит ячейку, включит тестовую сессию,
   применит среду, подготовит робот и последовательно выполнит сценарии.
6. Результат смотреть справа в истории: `PASS` — успешно, `FAIL` — нажать
   **Открыть FAIL** для загрузки проблемного сценария в редактор.

Для проверки Modbus выбрать `Python Modbus / Симуляция`. PLC должен обращаться
к IP компьютера с HMI (`127.0.0.1` для локального Runtime) и порту `502`.
Перед тестом один раз запустить `robot_simulator/run_simulator.bat` и оставить
его окно открытым. На экране тестов должны быть готовы `Test API` и Modbus.
Runner подключается к этому экземпляру и не запускает второй сервер.

Для стенда выбрать `SC-500 Modbus / Стенд SC-500 / Realtime`. Контроллер должен
быть готов, связь Modbus проверена, а физический ключ стенда включён. `Fast` на
стенде запрещён. Кнопка **Остановить** завершает прогон управляемо; после любого
завершения runner возвращает PLC в `NORMAL` и очищает тестовые инъекции.

## Режимы

`NORMAL` запрещает загрузку сценариев. `SIMULATION` использует модели станков и магазина PLC, а робот — SoftMotion либо Python Modbus. `SC500_BENCH` разрешён только с Modbus и физическим ключом `GVL_TEST_IO.xSc500BenchKeyInput`; адрес входа назначается в CODESYS при пусконаладке. После перезапуска PLC всегда выбирается `NORMAL`.

`FAST` доступен только в `SIMULATION`. Для SoftMotion коэффициент выбирается ползунком `1..100` на экране тестов. Изменение ползунка только запоминается: текущая траектория не перепланируется. Перед следующим принятым сценарием `FB_SIMULATION_DYNAMIC_LIMITS` останавливает движение, переводит группу в `GroupDisabled`, применяет `SMC_ChangeDynamicLimits` отдельно к X/Y/Z и возвращает группу через штатный `MC_GroupEnable`. Масштабирование выполняется как `velocity ×k`, `acceleration/deceleration ×k²`, `jerk ×k³`; тем же подтверждённым коэффициентом ускоряются таймеры PLC-моделей. При входе в SoftMotion-симуляцию FB сохраняет исходные лимиты осей, а при выходе в `NORMAL` восстанавливает их до разрешения следующего запуска. Для Python Modbus профиль `FAST` по умолчанию использует ×250 и дополнительно ускоряет внешний simulator. Бит `1108.9` (`0x0200`) подтверждает Python-симулятор; реальный SC-500 этот бит не устанавливает.

## Контракт сценария PLC

Gateway заполняет фиксированный `GVL_HMI.stTestScenario`, последним записывает ненулевой `udiLoadSeq` и подаёт импульс `xTestScenarioApply`. PLC атомарно проверяет и применяет буфер, затем отвечает `udiTestScenarioAckSeq` и `uiTestScenarioResult`.

Сценарий схемы v2 содержит число типов, три устойчивых состояния станков, две статичные кассеты по 120 слотов, признаки включения обоих магазинов, два захвата, ориентацию и начальные маски ошибок каждого владельца. Тип слота общий для обоих магазинов, как и в PLC-конфигурации. Старые сценарии v1 с одним `slots` автоматически мигрируют: данные идут в магазин 1, магазин 2 создаётся пустым и отключённым. Применение возможно только при активной тестовой сессии, остановленной ячейке и свободных технологических блоках. Координаты робота напрямую не записываются: HOME и захваты приводятся штатными командами.

После обновления PLC-исходников необходимо пересобрать Symbol Configuration: gateway ожидает `stTestScenario.axMagazineEnabled[1..2]`, `stTestScenario.aauiSlotContent[1..2,1..120]`, `stTestScenario.adwMagazineFaultMask[1..2]` и `stTestObservability.uiActiveMagazine`.

Тип слота задаётся всегда, в том числе для пустого слота: это назначение зоны
магазина типу изделия. Захват 1 допускает только заготовку, захват 2 — только
готовую деталь. Каждый десятый generated-сценарий намеренно некорректен и должен
получить от PLC `uiTestScenarioResult=2` до запуска цикла.

Маски начальных ошибок: cell `b0` — конфликт захватов; robot `b0` — неверная
команда, `b1..b4` — захваты, `b5..b8` — проверка точки; magazine `b0..b5` —
операция/no blank/no slot/invalid slot/content/geometry; machine `b0..b2` —
alarm/door/chuck, `b3..b10` — технологические timeout.
Один сценарий может иметь ненулевые биты только у одного первичного владельца; runner автоматически выводит из маски ожидаемый `uiErrorSource`.

Основные коды результата: `0` — применён; `1` — состояние не позволяет; `2` — неверные данные. Причины переключения среды публикуются в `uiTestRejectReason`.

## Хранение и запуск

SQLite-файл по умолчанию: `visu/gateway/data/tests.sqlite` (переопределяется `TEST_DB_PATH`). Таблицы:

- `test_scenario` — имя, описание, версия, JSON начального состояния и ожиданий;
- `test_run` — набор, среда, интерфейс, seed, прогресс и итог;
- `test_case_result` — PASS/FAIL, этап, причина и снимок PLC только при необходимости.

Экран «Сценарии и тесты» позволяет создавать, копировать, переименовывать, удалять и снимать сценарий с PLC, выбирать `smoke`, `regression`, `general` или `generated`, интерфейс робота, скорость, seed и количество комбинаций. Во время прогона gateway блокирует обычные команды HMI, кроме Stop и Reset.

Кнопка остановки посылает runner управляемый Abort. Перед завершением процесса runner останавливает цикл, очищает тестовые инъекции, возвращает `REALTIME`/`NORMAL` и снимает эксклюзивную сессию; принудительное завершение gateway применяет только при зависании очистки.
Если Python аварийно завершился, gateway повторяет эту очистку резервно и обязательно снимает `xTestSessionActive`.

`smoke` содержит 12 основных технологических случаев, включая взятие и укладку через магазин 2; runner сам отвечает на PLC-опросы о содержимом и типе груза и проверяет выбранный магазин и совместимый станок. `regression` содержит 73 воспроизводимых случая, включая семь проверок первичного владельца ошибки (оба магазина проверяются отдельно). `general` содержит восемь длительных вариантов полного производственного цикла: две исходные полные кассеты и две штатные перезагрузки дают последовательность партий М1-A → М2-A → М1-B → М2-B. В `generated` одинаковый seed создаёт одинаковый набор, каждый десятый сценарий намеренно некорректен, а полный цикл выполняется не более чем для 10% корректных комбинаций и максимум для 20 случаев.

Человеческое описание входов и ожидаемых результатов каждого фиксированного
случая приведено в [каталоге автоматизированных тестов](20-smoke-and-integration-test-catalog.md).

Gateway запускает `python -m robot_simulator.test_runner`, по умолчанию используя
`robot_simulator/.venv`. При нестандартном Python задайте `TEST_RUNNER_PYTHON`.
Для `Python Modbus` runner подключается к test-control API уже запущенного
симулятора (`http://127.0.0.1:8765`, переопределяется `ROBOT_SIM_CONTROL_URL`),
включает FAST при необходимости, а после прогона освобождает сессию и возвращает
PLC в исходную среду и интерфейс.

## Подключение в CODESYS

Добавить созданные DUT из `ST/ST_TEST`, `GVL_TEST_IO`, `FB_SIMULATION_DYNAMIC_LIMITS`, метод `PLC_PRG.RunTestControl` и обновлённые POU в проект через CODESYS, затем обновить Symbol Configuration. Бинарный `.project` и сгенерированные XML вручную не изменялись.

Перед первым стендовым тестом назначить физический вход ключа, проверить Modbus и запустить только утверждённое realtime-подмножество. Потеря ключа разрешает завершить текущую команду, блокирует следующую и приводит к FAIL прогона.

## Проверка

В каталоге `robot_simulator`: `python -m pytest`. В каталоге `visu`: `npm run test:gateway`, затем `npm run build`. PLC компилируется пользователем в CODESYS.
