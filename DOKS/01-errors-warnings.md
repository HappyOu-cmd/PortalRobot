# Как добавить аварию или предупреждение

## Архитектурное правило

В проекте источник события определяет только его владелец. `FB_ALARM_MANAGER` не знает бизнес-условий оборудования: он регистрирует подготовленные источники из `PLC_PRG`.

У каждого функционального блока есть два уровня ошибок:

- `Error.dwErrorActive` — все активные ошибки блока, включая ошибки дочернего оборудования и внешние причины. Поле нужно для автомата состояний, HMI и безопасной остановки.
- `Error.dwAlarmActive` — только собственные первичные аварии. Только это поле попадает в общий журнал.

Пример: при `GroupErrorStop` первопричину публикует `FB_AXIS_GROUP`. `FB_MOTION_MANAGER`, `FB_ROBOT` и `FB_CELL_MANAGER` переходят в ошибку, но не создают ещё три одинаковые записи в журнале.

Предупреждение не обязательно останавливает механизм. Оно фиксирует неверное действие оператора или нежелательное условие, которое PLC смог обработать безопасно.

## Добавление первичной аварии

1. Найти владельца физической причины: ось, группа осей, станок, магазин, робот, захват, менеджер точек или ячейка.
2. Открыть связанный тип ошибок `ST_<БЛОК>_ERRORS` и текущий `UpdateErrorView` блока. Добавить новый BOOL-флаг, комментарий на русском и свободный бит маски.
3. В блоке выставлять флаг только по фактической причине. `dwErrorActive` должен включать новый бит.
4. Если причина принадлежит этому блоку, включить тот же бит в `dwAlarmActive`. Если ошибка пришла от дочернего или внешнего блока, включать её только в `dwErrorActive`.
5. Дополнить текст ошибки в `UpdateErrorView`, чтобы оператор видел понятную причину.
6. Если у источника ещё нет отдельного значения в `E_ALARM_SOURCE`, добавить его в конец перечисления. Не вставлять в середину: старые числовые значения источников должны остаться неизменными.
7. В `PLC_PRG.st` добавить либо обновить элемент массива `astAlarmSource`: `eSource`, `dwAlarmActive` и `stWarning` владельца.
8. В `visu/src/plc/client.ts` добавить название источника и человекочитаемый текст кода аварии. Без этого журнал отобразит технический код или обобщённое сообщение.

## Добавление предупреждения

В диагностической структуре каждого блока уже есть `Diag.stWarning : ST_WARNING_EVENT`.

При возникновении предупреждения владелец должен записать код и увеличить последовательность:

```st
// Выполняется один раз по фронту недопустимой команды.
Diag.stWarning.uiCode := WARN_RESET_WHILE_ALARM;
Diag.stWarning.udiSequence := Diag.stWarning.udiSequence + UDINT#1;
```

Не увеличивать `udiSequence` в каждом цикле, пока условие остаётся TRUE. Для команды HMI использовать фронт импульса или флаг предыдущего цикла. Иначе журнал наполнится повторениями за несколько миллисекунд.

`FB_ALARM_MANAGER` сравнивает `udiSequence` с предыдущим значением. Каждое новое значение добавляет одну запись предупреждения, поэтому одинаковое предупреждение может корректно повторяться после нового действия оператора.

## Чего не делать

- Не формировать условие предупреждения в `FB_ALARM_MANAGER` для одного конкретного станка или одной кнопки.
- Не публиковать каскадную ошибку робота, если причиной уже является группа осей или захват.
- Не сбрасывать физически активную ошибку только программным сбросом.
- Не создавать новую структуру ошибок, если текущие `Error`, `Diag` и `ST_WARNING_EVENT` уже покрывают задачу.

## Цепочка до HMI

Текущий путь события:

```text
FB-владелец
  -> Error.dwAlarmActive / Diag.stWarning
  -> PLC_PRG.astAlarmSource
  -> FB_ALARM_MANAGER.Events
  -> GVL_HMI.astAlarmEvent
  -> OPC UA gateway
  -> visu/src/plc/client.ts
  -> панель аварий HMI
```

`ST_ALARM_SOURCE_DATA` и `ST_WARNING_EVENT` находятся в `Portal_robot/Device/application/ST/ST_ALARM`. Менеджер журнала находится в `Portal_robot/Device/application/FB/FB_ALARM_MANAGER.st`.

## Проверка

1. Экспортировать или импортировать обновлённые ST-файлы штатным Codescribe, затем выполнить `Clean` и `Build` в CODESYS.
2. Смоделировать первичную аварию. Проверить: один владелец добавил одну активную запись, зависимые блоки перешли в ошибку без дублей в журнале.
3. Нажать недопустимую команду один раз. Проверить одно предупреждение. Повторить действие: должна появиться новая запись.
4. Проверить `GVL_HMI.astAlarmEvent` через OPC UA и выполнить в `visu` команду `npm run build`.
5. Открыть HMI, убедиться в корректном названии механизма, тексте и цвете события.
