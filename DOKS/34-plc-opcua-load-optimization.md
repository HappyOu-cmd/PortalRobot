## Что изменено

| Данные | Полей в текущем снимке | Обновление |
| --- | ---: | --- |
| `astTwinStore` | 1444 | PLC копирует после изменения содержимого/подтверждений; gateway читает по ревизии |
| `astMagazineInventory` | 720 | После записи слота, смены банка, режима, сценария или инициализации |
| `astMagazineSlot` | 360 | Прежние PLC-пути сохранены; gateway получает совместимые поля из первого `astMagazineInventory` |
| `astAlarmEvent` | 600 | После добавления, деактивации аварии или подтверждения предупреждения |

Всего 3124 поля, около 45% обычного снимка, выводятся из постоянной проверки
больших значений OPC UA. Три таблицы — 2764 поля — читаются по изменениям;
ещё 360 совместимых полей формируются в gateway. Это объём устранённой
работы с данными; фактическую экономию CPU нужно измерить на MC522.

В PLC дополнительно:

- `FB_MAGAZINE` кеширует сводку по типам и первые свободный/заготовочный слоты.
  При изменении содержимого один проход заменяет прежние два полных прохода и
  два поиска. Пустые места считаются один раз, затем результат назначается типам.
  Без изменений проходов по слотам нет. Размер матрицы, число типов, внешний
  банк и тестовая инициализация инвалидируют кеш. Выбор операции сохраняет
  прежний порядок: сводка учитывает подтверждённые захват/укладку в том же скане.
- `RunTwoPallet` загружает рабочий инвентарь при смене банка/режима и после
  внешнего редактирования, а `RunMagazine` возвращает его в банк только после
  записи самим FB. Операторская палета и `axLoaded` имеют отдельный флаг изменения.
- `FB_ALARM_MANAGER` пересчитывает сводку 100 событий при изменении журнала.
  Полные копии FB → GVL_ALARM → GVL_HMI и поиск активного W52 выполняются тогда же.
  Проверка текущих масок аварий остаётся в каждом скане.
- FIFO ГК из 100 записей копируется в HMI при новом существующем
  `udiEventSequence` и при первой публикации. Протокол FIFO сохранён.

Расчёт базисов калибровки здесь не менялся. Частоты MainTask, SoftMotion,
координат, статусов, Ack/Result, I/O и диагностического опроса сохранены.

## Контракт ревизий и согласованность

Добавлен read-only родитель `GVL_HMI.stHmiDataRevision : ST_HMI_DATA_REVISION`:

| Поле | Назначение |
| --- | --- |
| `uiVersion` | 1 после первой полной публикации; до неё 0 |
| `udiEpoch` | TIME() первой публикации, отличает новый запуск приложения |
| `udiMagazineInventory` | Версия `astMagazineInventory` и совместимого массива первого магазина |
| `udiTwinStore` | Версия всех палет и `axLoaded` |
| `udiAlarmEvents` | Версия всех изменений журнала, включая снятие и подтверждение |

Перед копированием таблицы PLC увеличивает её ревизию до нечётной; после
копирования — до чётной. Gateway подписан на маленькую структуру ревизий
с sampling группы status. При уведомлении читает ревизии, только изменённые
родительские таблицы и снова ревизии. Таблица принимается при одинаковой
чётной версии и эпохе до/после чтения. Проверка независима для каждой таблицы:
изменение магазина не мешает принять устойчивый журнал аварий. Незавершённые
снимки повторяются через 100 мс; уведомление во время Read вызывает новый проход.
Результат старой сессии после disconnect не применяется.

Переполнение UDINT до 0 учитывается как новая чётная версия. При новой эпохе
таблицы перечитываются даже при совпадении чисел ревизий. Декодирование неполного
родителя или ошибка Read прерывает подключение; частичный снимок не публикуется.

Старые имена и типы PLC → gateway → HMI сохранены. При старом PLC без протокола
ревизий gateway использует прежние агрегированные подписки. Недоступный родитель
отдельной таблицы оставляет именно её на leaf fallback. Замена legacy-массива
возможна только при наличии точного источника для каждого его выбранного поля.

В `/api/health.monitoring.tables` доступны `protocol`, `roots`, `deferredFields`,
`aliasFields` и счётчики `stats.readRequests/tableReads/discardedTables`.
В ожидании после начального снимка `tableReads` должен оставаться постоянным.
`logicalItems` продолжает учитывать все поля HMI, включая совместимые.

## Применение в CODESYS

1. Создать DUT `ST_HMI_DATA_REVISION` из `ST/ST_HMI_DATA_REVISION.st`.
2. Обновить `FB_MAGAZINE` (декларации и реализацию) и его `UpdateTypeStatus`.
   Методы `FindBlank/FindFreeSlot` можно оставить: основной FB их больше не вызывает.
3. Обновить `FB_ALARM_MANAGER`, `AddEvent`, `DeactivateEvent`.
4. Обновить декларации `PLC_PRG` и методы `RunTwoPallet`, `RunMagazine`,
   `RunAlarms`, `PublishHmi`, `PublishGeometryControl`.
5. Добавить поле `stHmiDataRevision` в `GVL_HMI` и опубликовать всю структуру
   read-only в Symbol Configuration. Остальные поля оставить опубликованными.
6. Самостоятельно скомпилировать, сохранить и загрузить проект. После загрузки
   перезапустить gateway с обновлёнными `server.mjs` и `opcua-tables.mjs`.
   В health ожидаются `tables.protocol=1`, три корня, 2764 отложенных и
   360 совместимых полей для текущего состава проекта.

`.project`, сгенерированные XML и конфигурация задач вручную не редактировались.
Рабочий gateway автоматически не перезапускался. Изменения исходников сами
по себе не меняют исполняемый код контроллера и уже запущенного процесса Node.js.

## Приёмка и ограничения

Сначала сравнить одинаковое ожидание, затем одинаковый автоцикл: среднее/
максимальное время MainTask, jitter, CPU и счётчики чтения таблиц. Для нового
замера максимумов сбросить накопленную статистику Monitor штатной командой
Reset: прежние максимумы включают предыдущие состояния приложения.
[Описание Monitor CODESYS](https://content.helpme-codesys.com/en/CODESYS%20Development%20System/_cds_obj_task_config_monitor.html).

Проверить редактирование обеих палет, подтверждение загрузки, смену роли,
статичный/двухпалетный режимы, заполнение/очистку, тестовый сценарий, взятие и
укладку роботом, появление/снятие аварии и подтверждение предупреждений.
Контрольные признаки: таблица меняется после каждого действия; её версия
не растёт в ожидании; принятый gateway снимок соответствует целой PLC-версии.

Локальные проверки исполняют ST в ограниченной офлайн-модели и проверяют
gateway на синтетических ответах OPC UA. Для проверки журнала адаптер явно
возвращает скалярный `VAR_IN_OUT dwPrevious` владельцу; вложенные методы
сохраняют изменения полей FB. Эти проверки не заменяют компиляцию CODESYS,
работу на оборудовании и измерение CPU. Состав случаев —
[каталог тестов](20-smoke-and-integration-test-catalog.md#обновление-больших-таблиц-по-изменениям-02112026).
