# Проверка алгоритма ячейки в Python — 29.10.2026

Это исторический отчёт **до исправлений**. Текущие изменения и повторные
проверки F001–F006 находятся в [реестре 29](29-cell-defect-register.md).

Проверка обнаружила три воспроизводимых дефекта диспетчеризации. Рабочие PLC,
gateway и HMI не изменялись. Воспроизведение относится к ST-файлам рабочей
папки; соответствие загруженной в контроллер программы этим файлам не проверялось.

## Как устроена проверка

Пакет `robot_simulator/robot_simulator/plc_model` при запуске читает текущие
исходники. `st_runtime.py` разбирает используемое подмножество ST и исполняет
его в Python. Бизнес-логика не переписана вручную и не исправлена внутри модели.
Неизвестные конструкции, необъявленные поля и выход за границы массива дают
ошибку проверки.

Из исходников исполняются:

- весь `FB_CELL_MANAGER`, все его методы и вложенный инжектор;
- весь `FB_MAGAZINE`, методы проверки содержимого, выбора слотов и инжектор;
- весь `FB_GEOMETRY_CONTROL` и модель его конвейера;
- `F_GEOMETRY_SELECT_STATION`, `F_GEOMETRY_TAKE_DETAIL`, `F_GEOMETRY_EVENT`;
- адресные допуски Call/Cancel, обработка этих команд и условие автоматического
  запроса обмена из `PLC_PRG.RunGeometryControl/RunTwoPallet`;
- `FB_MACHINE` в коротких воспроизведениях ожидания оператора и таймаута люка.

Перечисления и структуры читаются из DUT: например, `E_PART_STATE.LOADED=2`,
`E_PART_TYPE.DETAIL=1`. Структуры копируются по значению; `VAR_IN_OUT`
сохраняет ссылку. Проверяются границы IEC-массивов, присваивания UINT/UDINT/SINT,
побитовые операции, вычисление всех операндов обычных `AND/OR`, отдельные `AND_THEN/OR_ELSE`,
CASE/FOR, фронты и таймеры TON/TOF с явными часами.

Один шаг модели выполняет запрос обмена → ГК → менеджер ячейки → обслуживание
станков → магазины → робот. Это порядок соответствующих вызовов в `PLC_PRG`.
Передача статусов между сканами сохраняется; новый маршрут не завершает
операцию мгновенно в том же вызове менеджера.

## F001 — Start не видит работу второго включённого магазина

Приоритет: P1 для запуска многотипной конфигурации.

Вход: два типа; С2 включён и пустой, закреплён T2; остальные станки выключены;
оба магазина включены; М1 содержит только заготовки T1, М2 — T2; захваты пусты.

Ожидается запуск через М2. Фактически менеджер остаётся в `IDLE`, выбирает М1,
публикует `xStartCheckTaskAvailable=FALSE`; повторный Start не меняет результат.

Причина: в `FB_CELL_MANAGER.st:341` до запуска `xMagazine1/2CanContinue`
равны механической доступности. Проверка полезной работы по содержимому
выполняется только при `xRunning` (`:345`). При первом выборе приоритет
достаётся М1; `SelectMachineBeforeTake/ForUnload` проверяют лишь его снимок
(`:688`), после чего `xStartCheckTaskAvailable` (`:792`) блокирует запуск.
До ветки, способной полноценно выбрать М2, автомат не доходит.

В матрице запуска это одна причина с множеством проявлений. Правильное
направление исправления: оценивать наличие допустимого первого задания в обоих
магазинах уже в IDLE, сохраняя текущий приоритет №1 при равных возможностях.
Рабочее исправление в рамках аудита не выполнялось.

## F002 — ожидание оператора на С1 перекрывает доступную работу М2/С2

Приоритет: P1 для непрерывной работы с разными типами.

Вход: два типа; ячейка уже запущена; С1 содержит заготовку T1 и ожидает
подтверждения запуска обработки оператором; С2 пуст и готов к T2; С3 выключен.
М1 содержит T1, М2 — T2; захваты пусты.

Состояние С1 получено настоящим `FB_MACHINE` через Enable → подтверждение
заготовки → `OPERATOR_CHOICE_RUN`, а не противоречивым набором искусственных
флагов. Станок включён, исправен, не Busy и не Processing, но не может принять
обслуживание.

Ожидается работа с М2/С2 независимо от ответа оператору на С1. Фактически
менеджер остаётся в `WAIT_TARGET` с М1, не выдавая операций.

Причина: проверка магазина в `FB_CELL_MANAGER.st:364` считает сам факт
загруженного изделия полезной текущей работой. Этого достаточно, чтобы
`xMagazine1CanSupplyBlank` стал TRUE и удержал приоритет М1 (`:416`), хотя
`SelectMachineBeforeTake` не допускает С1 ни как готовый, ни как обрабатывающий,
ни как start-pending станок. Выбор магазина и выбор станка используют разные
критерии существования продолжения.

Это голодание доступного маршрута, снимаемое внешним действием на С1;
аппаратная авария не требуется. Направление исправления: согласовать критерий
полезности магазина с фактическими маршрутами селекторов, сохранив выгрузку
из загруженного станка при наличии свободного места.

## F003 — отказ UNLOAD порождает постороннюю ошибку магазина

Приоритет: P1 для восстановления после локального отказа станка.

Вход: С1 содержит готовую деталь; заготовок в магазинах нет, в М1 есть место;
менеджер выбрал отдельный UNLOAD, оба захвата пока пусты. Люк С1 не открывается.

Настоящий `FB_MACHINE` исполняет штатный `UNLOAD_MACHINE` до `DOOR_OPEN`;
после подтверждённого снятия замка истекает `tDoorOpen`. Блок формирует только
`ERR_TIMEOUT_DOOR_OPEN=262144`, `xServiceRejected=TRUE`, локальную ошибку
без критического останова робота. Таким образом, отказ подтверждён исходной
машинной логикой и её таймером.

Ожидается исключение С1 и возврат к планированию оставшейся работы. Фактическая
цепочка менеджера:

```text
SERVICE_TARGET (UNLOAD, оба захвата пусты)
  → SELECT_FALLBACK
  → ERROR, ERR_MAGAZINE=4
```

Причина: ветви отказа/ошибки обслуживания (`FB_CELL_MANAGER.st:1752`)
безусловно направляют в `SELECT_FALLBACK`. Эта ветвь предназначена для
удерживаемой заготовки и считает `uiBlankPayloadType=0` ошибкой магазина
(`:1823`), хотя при ещё не начавшемся UNLOAD пустой захват корректен.

Направление исправления: после отказа выбирать продолжение по фактическому
грузу: пустые захваты → общий план; заготовка → альтернативный станок/возврат;
готовая деталь → действующий маршрут укладки/ГК. Первичная ошибка С1 должна
оставаться у С1.

## Перебор и воспроизведение

Команды выполняются из `robot_simulator`:

```powershell
.\.venv\Scripts\python.exe -m pytest
.\.venv\Scripts\python.exe -m robot_simulator.plc_model.audit --seed 20261029 --random-cases 64 --report "$env:TEMP/portal-cell-model-audit.json"
.\.venv\Scripts\python.exe -m robot_simulator.plc_model.audit --reproduce F001
.\.venv\Scripts\python.exe -m robot_simulator.plc_model.audit --reproduce F002
.\.venv\Scripts\python.exe -m robot_simulator.plc_model.audit --reproduce F003
```

Код возврата аудитора `1` означает нарушение, включая известные дефекты.
Полный JSON хранит входы, seed, последние переходы и SHA-256 исходных ST.
Известные дефекты в pytest — три `xfail(strict=True)`, а не успешные проверки
правильного поведения. Их нужно снять после соответствующего исправления PLC;
XPASS приводит к ошибке тестов.

Точный человеческий каталог фиксированных проверок и матриц находится в
[документе 20](20-smoke-and-integration-test-catalog.md#офлайн-модель-алгоритма-ячейки--29102026).

## Границы результата

Это полный перебор перечисленных конечных матриц, дополненный ограниченными
последовательностями, а не перебор всех состояний CODESYS или всех возможных
порядков событий во времени. Фиксированная проверка закрывает целую небольшую
партию для статичных магазинов и всех четырёх расстановок двух палет. Отдельно
проверяются последний слот 120/96, повторы/отмена Call, переполнение ID и W52.

Сервис станка в длительных последовательностях, завершение команд робота и
механика обмена палет заданы моделью успешной среды. Условие запроса обмена,
маршрутизация, инвентарь и ГК исполняются из ST; весь `FB_TWO_PALLET`, физические
цилиндры, SoftMotion, драйвер робота, таймеры реального обслуживания станков,
транспорт Modbus и безопасность оборудования полным перебором не проверены.

Баланс проверяется по типу изделия с учётом всех физических палет, станков,
захватов, занятых ГК и изъятых изделий. Неатомарное окно между подтверждением
робота Done и фиксацией переноса владельцем исключено из сравнения; после
освобождения Done расхождение уже недопустимо. Проверка прогресса требует
непрерывного существования допустимой работы 32 модельных скана без нового
действия; штатное ожидание занятого ГК или внешнего завершения не объявляется
самоблокировкой.

Компиляция и запуск CODESYS не выполнялись. Изменений аварий, предупреждений,
OPC UA-тегов, бинарного проекта или журнала SQLite не было.
