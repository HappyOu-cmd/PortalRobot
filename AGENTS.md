# CODESYS Project Rules

- Рабочая папка приложения:
  `Portal_robot/Device/application`.
- Вся PLC-логика пишется только на IEC 61131-3 Structured Text (ST).
- Не создавать логику на LD, FBD, CFC или SFC.
- Перед написанием или изменением кода обязательно изучить официальную
  документацию CODESYS для используемых POU, типов и библиотек.
- Для стандартных motion-блоков сверяться с документацией SM3_Basic,
  SM3_Robotics и SoftMotion.
- Не придумывать входы, выходы, состояния и поведение библиотечных блоков.
- Использовать в первую очередь официальную документацию:
  https://content.helpme-codesys.com/
- Перед изменением POU изучить связанные DUT, GVL и вызывающие блоки.
- Перед программированием отдельного FB изучить все его будущие связи с
  другими блоками: кто формирует его входы, кто использует его выходы, какие
  GVL и DUT он читает или изменяет, а также в какой задаче и последовательности
  он вызывается.
- Не создавать новую структуру данных, если в проекте уже существует структура,
  соответствующая назначению блока. Сначала использовать и развивать текущую
  архитектуру проекта. Новую структуру добавлять только после анализа связей и
  отдельного согласования.
- Не редактировать вручную бинарный `.project` и сгенерированные XML без
  отдельного согласования.
- XML, созданные штатным экспортом Codescribe и необходимые для восстановления
  визуализации, GVL, конфигурации задач и других объектов приложения, хранить в
  GitHub и синхронизировать вместе со связанными ST-файлами.
- После изменений проверять проект сборкой CODESYS. Если сборка недоступна,
  явно сообщать об этом.

## Visual Reference Rules

- Если пользователь присылает визуальный референс интерфейса, реализовывать
  дизайн строго по нему, сохраняя композицию, размеры, отступы, типографику,
  цвета, иконки и визуальную иерархию настолько точно, насколько это позволяет
  функциональность проекта.
- Работа с референсом всегда выполняется в следующем порядке:
  1. Внимательно изучить референс и выделить его ключевые визуальные параметры.
  2. Внести необходимые изменения в интерфейс.
  3. Запустить интерфейс, сделать контрольный скриншот в целевом разрешении и
     визуально сверить результат с референсом.
  4. Если сверка неудовлетворительна, продолжать исправления и повторять
     проверку до максимально точного совпадения с референсом.
- Не считать задачу по визуальному референсу завершённой без запуска интерфейса
  и визуальной проверки результата.
- Не заменять показанные в референсе решения собственными дизайнерскими
  интерпретациями без явного согласования с пользователем.
- Контрольные скриншоты делать при масштабе браузера `100%` и в целевом
  разрешении; масштаб элементов должен соответствовать референсу.
- Проверять, что выбранный шрифт действительно подключён. При необходимости
  загрузить его локально вместе с проектом.
- Иконки должны соответствовать референсу по виду, размеру и толщине линий.
  Активное состояние включает также показанный в референсе фон элемента.
- Иконки Flaticon использовать только при точном соответствии референсу. Если
  подходящий файл невозможно загрузить, запросить его у пользователя и не
  подменять произвольной иконкой.
- При сверке отдельно сравнивать цвета фона верхней панели и основной области.

## Frontend Stack Rules

- Рабочая папка React + TypeScript визуализации:
  `C:\Users\KOKSHAROV IR\Desktop\Project\Portal robot\visu`.
- Перед подключением или обновлением frontend-библиотеки проверять текущие
  зависимости в `package.json` и не устанавливать уже подключённый пакет повторно.
- Перед использованием API Tailwind CSS, Radix UI, Recharts, Iconify и других
  развивающихся библиотек сверяться с актуальной документацией через Context7 MCP.
  Если Context7 недоступен в текущей сессии, явно сообщить об этом и использовать
  официальную документацию библиотеки.
- Iconify использовать для промышленных и интерфейсных иконок. Перед добавлением
  иконки проверять существование её точного идентификатора. Не подменять
  отсутствующую иконку произвольной без согласования.
- Radix UI использовать как техническую основу диалогов, подсказок, вкладок и
  выпадающих меню. Внешний вид создавать самостоятельно в стиле проекта; не
  оставлять стандартное оформление библиотеки.
- `class-variance-authority` использовать для вариантов повторно используемых
  компонентов и их состояний. Для сборки классов применять общий helper `cn()`
  на основе `clsx` и `tailwind-merge`.
- Tailwind CSS 4 использовать как дополнительный слой утилит через Vite-плагин.
  Не подключать Preflight и не переписывать существующие `theme.css` и
  `styles.css` без отдельной необходимости: текущая HMI-вёрстка должна сохранять
  размеры и поведение.
- Recharts использовать для статистики станков, робота, циклов, простоев и
  аварий. Цвета, подписи, шкалы и плотность графиков должны соответствовать
  промышленному интерфейсу и существующим токенам темы.
- shadcn/ui допускается только как техническая основа отдельного компонента.
  Не копировать его стандартный дизайн и не переносить в проект лишние
  зависимости или компоненты.
- Не создавать типовой нейросетевой интерфейс с чрезмерными скруглениями,
  крупными тенями, градиентами, декоративными панелями и пустыми карточками.
  Интерфейс должен быть компактным, предсказуемым и удобным для сенсорного
  промышленного экрана `1920x1080`.
- После изменений frontend-конфигурации или базовых UI-компонентов выполнять
  `npm run build` и проверять интерфейс при масштабе браузера `100%`, включая
  отсутствие ошибок консоли, переполнения и смещения Three.js-сцены.
